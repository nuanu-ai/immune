# immune-contract

The Rust types of Immune's contract, package `immune.v1`: the messages the commands of the contract print, in binary protobuf and in Immune's own JSON. It carries the repository's MIT licence.

The schema in `immune/v1/` is the source. `src/immune.v1.rs` is generated from it and committed, so a build needs no `protoc`. `samples/` holds real answers of the core, a status and a finding of every kind of evidence made on an invented Mac, for a client to test its decoding on; `tests/contract_samples.rs` makes them again and fails when they no longer have the shape the core gives. The major version is the contract's `format`; see [the reference](../docs/reference.md#the-contract).

Depend on it by a git path at a commit: `immune-contract = { git = "https://github.com/nuanu-ai/immune", rev = "<commit>" }`.

Read binary output with `immune_contract::prost::Message`, as `v1::Known::decode(stdout.as_slice())`, and JSON output with any serde parser, as `serde_json::from_slice::<v1::Known>(&stdout)`.

## Who reads it

[Artificial Immunity](https://immunity.bot) is a closed product from Nuanu AI Lab built on top of Immune. It decides what to do about a finding: triage with a model, response, handing work to an agent. It runs the `immune` binary unchanged and shares no code with it except these types. Immune does not stream every event out. Immune works on its own and does not need Artificial Immunity.

## Events, matches and findings

An event (`Event`) is something that happened on the Mac and that the collector recorded: a program start, or a file created or renamed. The core keeps no event; it reads them again from a log that lives about a day.

A match (`RuleMatch`) is one rule that matched one event. On its own it claims nothing. There are many, and the app does not list them. `immune matches` gives every one, of every level, with its event, for a program that judges them.

A finding is what the core decided a person should look at. There are few, and each stays open until the person answers it, except a finding about a state, such as a malicious package in a lockfile, which the core clears when the state goes. `immune findings` lists them.

A match of a rule marked below high raises nothing, and its `raised` is `below_high`; so does a match of a rule whose set states no level, with `level_not_stated`. A match of a rule marked high or critical also raises that rule's finding or adds to the one it has, so it is in both answers. Its `raised` is `finding` once the core's own reading has read the line, and `findings` names the finding. Many findings rest on no event at all: a malicious package, or a shell startup file that changed. A `suspicious` verdict raises a finding of its own.

## What the contract covers

The messages of the contract are the answers of `immune matches`, `immune findings`, `immune finding`, `immune project`, `immune program`, `immune machine`, `immune status`, `immune rules`, `immune vulnerabilities`, `immune owner` and `immune sample`, the `Verdict` a program sends to `immune verdict` and the `VerdictRecorded` it gets back, and `Failure`.

Unknown is never zero and never false. A count, a total or a yes-or-no the core could not establish is an optional field that is absent (null in JSON), or it sits inside a message that is absent. A section the core could not give is absent and named in `not_computed` with the reason; a list that is there and empty means there is nothing in it. A reader that takes an absent number as 0 or an absent yes-or-no as `false` reads calm the core did not establish.

## A client to start from

[`examples/client.rs`](examples/client.rs) runs the loop below with the types of this crate and nothing else. It reads the matches page by page and prints each one, counts the open and urgent findings, and with `--judge-first` sends a `suspicious` verdict with a `verdict_id` about the first match. It then sends the same verdict again, which is answered with `already_recorded`, and a changed one under the same id, which is refused with `verdict_id_reused`. A verdict is written into the store, so point it at a store made for trying it:

```sh
cargo run -p immune-contract --example client -- --immune <path to immune> --store <path> \
    [--after <place>] [--judge-first] [-- --system-root <dir>]
```

Without `--store` it stops, so it never writes to the default store. Arguments after `--` go to `immune matches` and `immune verdict`. The test [`tests/contract_client.rs`](../tests/contract_client.rs) runs it against the core as built.

## The loop of a program that runs the core

A program that judges what the core found runs four commands. Name the form on every call, `--proto` or `--json`: without one, a command prints text for a person, and `immune verdict` is refused. Check the exit code first: a failure is the message `Failure`, in the form named.

1. `immune matches --proto --after <continue_after>` gives the rule matches since the last call, each with the event it matched, its rule and `raised`, what the core did with it. Keep `continue_after` whole and pass it back. What its `collector` says arrives of the fields a later collector keeps is the core's latest reading, at `status_read_at`, not the stretch. Whether an answer is quiet rests on `unevaluated`, which covers the lines the answer read: a rule that reads a field is listed when that reading says the field does not arrive, and also when some line of the answer did not give it. A group that only some lines fill by nature, as `script` is, is judged by the core's latest reading alone: one start without a script cannot tell a program that runs none from a field the collector stopped filling. After the collector stops filling such a group, an answer over lines the core has not read yet can stay quiet until the core's reading has counted the group's bound, 1,000 program starts for `script`, and for as long as the core does not read at all. No shipped rule reads such a group. A match of a rule whose set states no level has `raised` `level_not_stated`: the core raised nothing and leaves the judgement to the reader. The value 5 of `raised`, `RAISED_UNRECORDED`, is reserved since 1.14.0: a store of this format records which finding each match went to from its first reading.
   A program start's `args_text` has the secrets the core recognises cut out. Each cut is a mark, `\cut{<kind> <length>}`, and the start's `cuts` lists them, one per piece, with `argument`, `kind` and `length`. Go by `cuts`, not by the marks in the text. Since 1.6.0.
   To put matches together by the process they belong to, use what an event says of its processes. A program start's `process` and `instigator`, and a file event's `instigator`, carry the pid with `pid_version` and `started_at`, and the ids of the audit token: `user_id`, `real_user_id`, `group_id` and `real_group_id`. A program start also has `parent`, `responsible` (the process macOS holds responsible for it) and `process_group_id`. A line written by a collector installed before these were kept gives only the started program's `pid` and `user_id`, and the rest are absent. `real_user_id`, `group_id`, `real_group_id`, `responsible` and `process_group_id` since 1.12.0.
   Who signed a process is in `signing_id_text`, `team_id_text`, `platform_binary` and `codesigning_flags`, for the program started, for the process before the `exec` and for the process behind a file event. Each is absent where the line does not give it, as on a line an earlier collector wrote. Since 1.13.0: `signing_id_text`, `team_id_text` and `platform_binary` of the process before the `exec`, and `team_id_text`, `platform_binary` and `codesigning_flags` of the process behind a file event.
2. `immune findings --proto` lists the findings, and `immune finding <id> --proto` gives one with its evidence and the person's answer. `kind_title` is a finding's `kind` as a person reads it, such as `Shell startup file` for `shell profile`; match on `kind`. A `watched.first-read` finding has `thing`, the places its check read for the first time counted by kind, and the machine in `where_text`. Since 1.8.0. A finding of a rule this build does not have is listed too, with the `kind` `finding of a rule not in this version`, its `rule` as the store keeps it, and `severity` and `confidence` absent. A reader on an older version of this crate fails on that null `severity` in JSON and reads binary as `unspecified`. A finding and a listed finding carry `short_title`, a name of at most 44 characters for a list; a listed finding of a published rule carries the rule's own title in `rule_title_text`, and one about a package a lockfile declares carries `package_text` and `releases_text`. `Status.needs_a_look.by_rule` counts every open finding by its rule. Since 1.16.0.
3. `immune project`, `immune program` and `immune machine` answer what the store knows of a thing, with coverage. Their `findings` are those about the thing under every id in `same_as` and about anything inside it at any depth, so a machine's include its projects' packages. A Homebrew formula and its kegs are one program, and so are an application and the code it keeps in the Library folder: asked by any of them, the answer names the others in `same_as`. Since 1.18.0.
4. `immune verdict --proto` reads one `Verdict` on standard input and answers with `VerdictRecorded`.

A `Verdict` names what it is about, a match by the `position` and the rule's `name` as `immune matches` printed them, or a finding by its `id`, and carries the `store_id` of the answer it judged. Its `kind` is `suspicious` or `harmless`. `reason_text` and `case_text` are required. `severity` and `confidence` are required on a `suspicious` verdict and refused on a `harmless` one.

A `Verdict` may carry `verdict_id`, an id you make for it that nobody can guess, such as a UUID: 1 to 200 characters of printable ASCII, `!` to `~`, with no backslash. It is a token, not text, and comes back exactly as sent. Send it again after a failure with the same id and the same content, and you get the verdict recorded then with `already_recorded` true, whatever became of its finding or its line since; nothing is written. The same id on a message that differs is refused with `verdict_id_reused` and nothing is recorded: send a real decision again under a new id. A repeat after the person answered the finding gets the earlier `recorded_at` and raises nothing, so a new decision needs a new id. Without an id, the same message is recorded once while its finding is open. A `suspicious` verdict about a match whose line has left the log is recorded with `RecordedVerdict.event_gone` true: the core did not read the event again or check that the rule matched it. A `harmless` one about such a line is refused with `match_gone`. Since 1.17.0.

A secret the core recognises in `reason_text` is cut where the reason is kept, and the verdict is recorded: `RecordedVerdict.reason_cuts` lists what was cut. A mark quoted from the core's output, bare or with its backslash doubled as JSON writes it, is a value already cut and is kept as text, so a reason can quote what the core printed. A key holding a secret is refused with `holds_secret` and is never rewritten: `case_text`, `verdict_id`, `store_id` or what the verdict names. A failure cuts what it repeats of what it was sent. Since 1.6.0.

To keep the words of a quote of the core's output, quote it as the text form prints it, or leave a space after each cut value. A mark glued to more text in its word, as compact JSON writes `"…\cut{immune:flag-value 11}"],"cuts":`, starts a value that goes on, and the rest of that word is cut as after a real value. The reason is still recorded with every mark it quoted, and `reason_cuts` lists the cut.

The person's reasons are cut the same way: an `Answer` in `immune finding` and `immune status`, and a `Statement` or `Said` in `immune owner`, carry `reason_text` cut and `reason_cuts` beside it. Cutting always runs, so an empty `reason_cuts` means nothing was cut. Since 1.7.0.

`immune vulnerabilities` names in `unknown` the packages for which it cannot be told whether a record affects them, each with its project, its ecosystem and the first reason, at most 200, with `total`. It names in `unread` each project's lockfiles of one ecosystem that were not all read, such as a project with only a `yarn.lock`, with why, whether or not a package was read there, as `no_reader` a project's lockfiles of a kind this version has no reader for, such as `go.sum`, as `not_read` with the ecosystem `any` a project the reading of lockfiles did not open, and as `none_found` a project in which no lockfile was found; a project with any of these is never `not_affected` for any record. `totals.places_not_read` and `totals.projects_not_read` count them, `totals.projects_without_lockfile` counts the projects with no lockfile apart, which get no answer for a record, and `totals.projects_compared` the projects compared with current data with nothing left unread. In `immune vulnerability <id>` for an id no record names, `said` counts the projects for which it cannot be told, and why, before it says which it does not affect; with no project to compare, it says that it cannot be told. A record no project could be compared with is not `answered`, and its `said` says why. Since 1.18.0.

`totals.projects_found` and `Vulnerability.projects_found` say whether every place this version looks for projects in was looked into at the latest check, with no folder macOS protects met there and left out. They do not claim every project on the Mac: what this version does not look in by design is a limit named in the reference. While `all` is false, every count and every "does not affect" speaks only for the projects found, `why` says why, `cause` is `not_given` for a place the check was not given or does not enter and `failed` for a reading that failed or a finder with no reading of this Mac, and `folders_text` names the folders macOS protects that were left out, a disk by the name the Mac gives it. Show calm about the projects as a whole only when `projects_found.all` is true. A core before 1.21.0 does not say, so a message without it is not known, never all. Since 1.21.0.

What `immune status` does not cover is one item per cause in `not_covered`. Each cause names what it is about in `examples_text`, by name only. `examples` lists the same things in the same order, each with `name_text` and `reason_text`, what its source said about it, such as why a server could not be opened. The secrets the core recognises are cut out of a reason, as in `args_text`, and `reason_text` is absent when the source said nothing. The `reason_text` of `coverage.problems` and `coverage.unreached` is cut the same way. Since 1.8.0. A cause's `class` says whether it is a failure (`failed`), something this version does not read (`no_reader`) or something its source does not give (`not_given`), whoever can fix it; `unspecified` is read as `failed`. Since 1.16.0.

`immune on` and `immune off` answer with `Service`. Its `in_place` says whether the login job runs the core where it is, because only root can replace it, or a copy in the store's folder; after `off`, judged of the core running the command and never of the job's property list, a core run where it is is still at `program_path_text`. Its `started` says whether the job's watcher came up within a few seconds after `on`: it holds the store and its heartbeat is fresh. Its `watching` says whether that watcher watched the store live by then, which follows its first check, with `watcher_note` when it did not. Both are absent when that could not be told: read absent as not known, never as no. With no watcher on the store, `Status.login_job_installed` tells a job installed and not running from one not installed, and `Status.watcher_restarting_since_at` says the watcher left because its file was replaced and launchd is starting it again. Since 1.19.0. `immune off` records that it turned Immune off in the store's journal, and the job's watcher records that Immune is on at its first reading after `immune on`, which writes nothing itself; `Status.turned_on_at` and `Status.turned_off_at` give the latest of each, and `Status.turned_on_latest` which came last in the journal's order: a job not installed whose latest is `turned_on` went off by something other than `immune off`. When `immune off` could not write its entry, `Service.not_recorded` says why, and the command succeeded all the same. Since 1.20.0.

A verdict never changes a finding the core raised. A `suspicious` one raises a finding of the rule `verdict.suspicious`, with the verdict's levels, which the person closes. A `harmless` one is kept and shown beside what it is about. The whole of it is in [the reference](../docs/reference.md#immune-verdict).

The person can answer the core's finding and the `verdict.suspicious` finding of the same rule and thing with one command, `immune finding <id> seen|expected … --with <other id> --journal-seq <n>`, and take both answers back with `reopen --with`. Name the other finding yourself: a finding the command does not name is never answered. From the core's finding, `verdicts.verdict_finding` names the other while it is open or expected. From a `verdict.suspicious` finding, nothing points back: look in `immune findings` for the finding whose `finding.rule` is the `verdict_given.rule` of its evidence and whose `finding.about_text` is the same, and for `reopen --with`, where the other is seen or expected and no longer named, look the same way. The pair is checked by rule and thing, and each answer refuses a finding it cannot answer.

`--journal-seq` is the `journal_seq` of the answer the person was shown, from `Finding`, `Findings` or `Status`; when the two findings came from two answers, pass the smaller. The answer is refused with `changed_since_read` when, after it, a finding it answers gained a match of its rule, a newer reading it rests on, a verdict, an answer given or taken back, its clearing, or the end of an `expected` mark that a check recorded. For the core's finding the same holds for the `verdict.suspicious` finding of its rule about the same thing that it shows in `verdicts`, one raised since included. `detail_text` names the finding that changed: read again and show the person what is new. A new match of the finding's own rule refuses `seen` and `reopen` but not `expected`, which already quiets every later match of the rule; a verdict and everything else refuse all three. Both answers are recorded or neither is, and each is kept as an ordinary answer on its own finding. The answer's `answered_with` gives the other finding as the command left it. A finding named by `--with` that is not the other of the pair is refused with `not_the_pair`, and nothing is recorded. As with any answer, run it only with the person's agreement. Since 1.9.0.
