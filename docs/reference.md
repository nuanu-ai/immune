# Reference

What Immunity Core reads on a Mac, where it looks, what it records and when; the vocabulary of facts; the commands and the contract; and the files it keeps. [how-it-works.md](how-it-works.md) explains the terms used here.

## Events, matches and findings

An event is something that happened on the Mac and that the collector recorded in its log: a program start, or a file created or renamed. The store keeps no event.

A match is one rule that matched one event. On its own it claims nothing. There are many, and the app does not list them; [`immunity matches`](#immunity-matches) gives every one, of every level, for a program that judges them.

A finding is what Immunity Core decided a person should look at. There are few, and each stays open until the person answers it, except a finding about a state, which Immunity Core clears when the state goes. [`immunity findings`](#immunity-findings-and-immunity-finding-id) lists them.

A match of a rule marked below high, or of a rule whose set states no level, raises nothing. A match of a rule marked high or critical also raises that rule's finding or adds to the one it has, so it is in both answers. Many findings rest on no event at all, such as one about a malicious package in a lockfile or a shell startup file that changed.

## What is watched

| What | How | When |
|---|---|---|
| Places where persistence lives: launch agents and daemons, login and logout hooks, zsh and bash startup files, `~/.ssh/config`, `authorized_keys` and `rc`, the system's SSH configuration, PAM policies and modules, authorization plugins, git hooks in every project | A checksum of each file, never its content; for login hooks, a checksum of the hook alone | Within seconds while the watcher runs, otherwise at a full check |
| Software changed in place: app bundles, Homebrew kegs, global npm packages, code that apps keep under Application Support | The app's code signature, verified by macOS; for the rest, a digest of file paths and change times | At every full check |
| Files that make a tool run code by itself: package install scripts and pnpm hooks, editor tasks that run when a folder opens, editor and dev container settings, coding agents' settings, hooks and MCP server lists, editor extensions | A checksum of the file or the part that runs code. 14 of the 41 known ways in a project and 7 of the 11 known places in the home folder are read | At every full check, and within seconds for most while the watcher runs |
| Dependencies in `package-lock.json`, `pnpm-lock.yaml` and `Cargo.lock` | Matched against OSV's data for npm and crates.io and against CISA's catalogue | At every full check |
| The user's running programs and their internet connections | Read without administrator rights. An interpreter given code on its command line and left running without a terminal is a finding | Every 30 seconds while the watcher runs |
| Every program start and every file created or renamed, with the collector | Checked against 198 published rules for macOS: the 75 of SigmaHQ, and 66 of Elastic's detection rules and 57 of its behaviour rules translated into Sigma. 175 are evaluated in full and 23 in part | About every 10 seconds while the watcher runs, and at every check |
| Indicators from an incident report that the user gives as `indicators.json`: SHA-256 hashes, domains, IPv4 addresses, URLs | Matched against watched files, lockfiles, editor tasks and connections | At every check |

## What this version does not see

`immunity status` lists what is not covered, one item per cause, and says who can act on each (see [how-it-works.md](how-it-works.md#coverage)). Today the limits of this version include:

- A connection at the moment it is made, and the name behind an address. Immunity Core samples connections every 30 seconds and sees addresses only; `eslogger` has no network event.
- A file modified in place or removed. The collector records files created and renamed only.
- `fork` and `exit`: a process that forks without starting a new program, and when a process ends.
- One of SigmaHQ's rules, 12 of Elastic's translated detection rules and 10 of its translated behaviour rules have an alternative that needs a field `eslogger` does not give, or that the translation could not carry, so they are evaluated only in part. Of Elastic's other 119 detection rules for macOS, none is evaluated: 30 correlate a sequence of events, 40 are written in KQL or ES|QL, and 49 need events or fields the collector does not record or could not be translated exactly. Of its other 221 behaviour rules, none is evaluated: 109 correlate a sequence of events, and 112 need events or fields the collector does not record or could not be translated exactly. `immunity rules` names each with its reason.
- Without the collector: the moment a program starts, its command line, who started it, and which program created a file. The published rules then do not watch.
- Vulnerabilities in installed apps, Homebrew packages, what servers run, and projects in other languages. Lockfiles Immunity Core has no reader for, such as `requirements.txt`, `uv.lock` or `go.sum`, are named in the report, and so are lockfiles it reads but did not open because they lie more than 4 folders deep or in `vendor` or a hidden folder. A lockfile is known only by its file name, so one whose name is on no list Immunity Core keeps is not found, and its project can read as wholly read.
- Software installed by any package manager other than Homebrew and npm. Immunity Core names a few when it finds them at their installers' default places (MacPorts, Nix, pkgsrc, Fink, conda, and npm under nvm), reads nothing they installed, and does not find the rest. Homebrew and Tailscale installed outside their default places are not found either. One that an earlier check read and this one does not find is reported as not found now, and what was known from it is kept.
- Folders macOS asks permission for: Desktop, Documents, Downloads, iCloud Drive, other cloud storage, other apps' containers and anything under `/Volumes`. Immunity Core never enters them, so macOS never shows a permission dialog because of it. The report names those it met on the way, and the projects page says which folders the search for projects does not enter. A new project kept there is not found; one found there before stays listed as it was.
- New projects in a folder on another file system than the one the search for projects starts on, such as a container tool's view of its containers, a mounted disk image or a network share. Such a folder may hold your own work: a project there is found when a coding agent works in it, or when `--checkouts-root` points into it.
- Which program changed a watched file in place.
- Stopping anything. Immunity Core reports, and it never blocks, suspends or kills a program.

## When readers run

| Name | Trigger |
|---|---|
| full check | `immunity run` on request. `immunity watch --background` also starts one at startup and every hour, with a 30-minute limit. See [the background service](core-service.md). |
| live | `immunity watch`, about a second after FSEvents reports a change in a place it subscribes to: the readings that place belongs to, or every place, see [Watched places](#watched-places) |
| sample | `immunity watch` every 30 seconds, or `immunity sample` |
| events | `immunity watch` every 10 seconds, and at every full check |

No reader enters a folder macOS asks permission for, whether a path names it, spells it otherwise as the volume folds names (`~/Deſktop` is `~/Desktop`; such a folder is told by its device and inode), or a symbolic link leads into it: Desktop, Documents, Downloads, iCloud Drive, `~/Library/CloudStorage`, `~/Library/Containers`, `~/Library/Group Containers`, and anything under `/Volumes`. So Immunity Core never makes macOS show a permission dialog. A reader that skipped one writes a reading of the kind `folders macOS asks permission for` naming them, and checkouts already known there are kept with nothing inside them read. A new project kept in one is not found: the status names the folders under `protected-folders`, and the page's list of projects says they were not looked into, beside what the search for projects does not enter by design, from its own limits: the home folder's Library, which holds iCloud Drive and other cloud storage, hidden folders, links to folders and anything deeper than five folders.

Every list on a page takes its empty text from the coverage of what fills it: it says there is none only when every such reading is full and taken by the latest check; otherwise it names what was not read, why, and when it was last read in full. `--checkouts-root` can point a full check into such a folder on purpose.

For each session file, `agent-folders` keeps in the store's `session_file` table the end of the last whole line it read (the position), the SHA-256 of the bytes before it, the working folders those bytes name, and the file's inode and change time. No other text of a session is kept, and the working folders are never printed. The store keeps at most 64 folders per file, each at most 1024 bytes, and 4 MiB over all files; a file past these bounds is read from its first byte every time. The next reading goes on from the position only when the file has the same inode and either its change time has not moved since a reading taken at least a second after it last changed, or the bytes before the position hash to the digest kept. The first of these, which reads nothing before the position, is used only on APFS and HFS+ volumes, by the type name `statfs` gives. There the kernel moves the change time on a write, a change of size and a change of the modification time, and no program can set it. On any other volume, such as FAT, exFAT, SMB, NFS or FUSE, the bytes before the position are hashed on every reading. Even on APFS and HFS+, changed bytes are not seen until the change time moves in two cases: a write through a shared mapping of the file, until the mapping is synced or unmapped, and a change to the volume while it was not mounted. A program that can do either can also rewrite the session file outright, and a reading from the first byte would see no more. Any other file is read from its first byte. A last line without its line break is read, and read again the next time. A session file is a regular file in its folder of sessions, opened without following a link and without waiting: an entry that is a link, a named pipe or, for Codex CLI, a folder is a session file that could not be read. Below a Claude Code project's folder a folder is entered whatever its name. Where a folder would be entered, a link is not followed and counts as a folder that could not be listed, and the reading is partial. At most 64 MiB of a line is held; the rest of a longer line is passed over, and the line is counted as not parsed. A file whose working folders come to more than 256 KiB could not be read. A compressed session does not grow, so it is read whole or not at all: its position is its length and its digest is the SHA-256 of its compressed bytes, trusted by the same rule, and a trusted one is not decoded again. It is decoded as a stream, never whole in memory, and no further than its length when it was opened. One that is not a single zstd frame with nothing after it, is cut short, asks for a window over 128 MiB or decodes to more than 1 GiB is a session file that could not be read, gives no working folder, and the reading is partial. The frame's checksum is not checked. Deleting the rows of `session_file` makes the next reading start from the first byte of every file.

A command line is read by `processes` only for seven kinds of interpreter (node and bun, deno, python, ruby, perl, the shells, osascript), only to decide whether it was given code on its command line, and it is dropped there. It is never stored, printed or returned.

### Threat data

Read at every full check, not as readers of the Mac: CISA's catalogue and OSV's archives for crates.io and npm. Each attempt is a row in `feed_reading`. See [threats.md](threats.md).

A download that failed is one item of `not_covered`: since when the data is old, and why, in fixed words for each of curl's documented exit codes (curl(1), EXIT CODES), for the HTTP status, or for a body that was not the data, one case whatever the source. `who` is `you` only when the cause is certainly this Mac's or its network's to fix: a download that could not be written on the disk, a certificate this Mac does not trust (its clock may be wrong, or the network may inspect encrypted traffic), or a proxy that asks for a password or fails its own handshake. Those are `vulnerability-list-not-downloaded-fixable` and `vulnerability-data-not-updated-fixable`. Anything else, such as a refusal by the server or something between, a name that does not resolve or a connection that fails, is `vulnerability-list-not-downloaded` and `vulnerability-data-old`, with `who` `nothing`. What curl said is in `value_text`.

Downloads use a proxy only when the core's environment names one, as `/usr/bin/curl` does. On a network that requires a proxy, run a manual check from a shell with the proxy set in its environment. If the background service cannot reach the feeds, coverage reports the download failure.

## Watched places

36 rows of the table of autorun points, `POINTS` in `src/autorun.rs`, the same table as the ways below. Adding a place is adding a row. Each kind is one reading. After a change, a watcher first reads only the readings whose places the change is in, each whole: one kind of place on this Mac, the hooks of one checkout, or one row of what runs by itself in every checkout. Every other reading keeps its own time in coverage. A watcher reads every place at its start, whatever the store says of an earlier one, after a reading that failed, when it finds new places to watch or a new way into one, after events FSEvents says it dropped or coalesced, for a change at a path in no watched place, and at its next look at what to watch, once a minute, after any reading of some places or when a watched path now leads somewhere else. The place a change names is read within seconds, every other place within about a minute. So what a watcher still owed when it stopped, and what changed while none ran, is read at the next start; on a Mac where nothing changed, that reading's `read` line has `new`, `changed`, `gone` and `opened` at 0. The `watcher` row keeps when every place was last read. A place a later version reads for the first time on a store that already exists is read for the first time: what it holds is its baseline and is told once by `watched.first-read`.

| Kind | Places |
|---|---|
| `autostart item` | every entry in `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons` |
| `login or logout hook` | the `LoginHook` and `LogoutHook` keys of `/Library/Preferences/com.apple.loginwindow.plist` and `~/Library/Preferences/com.apple.loginwindow.plist`, each as `<file>#/<key>` |
| `shell profile` | `/etc/zshenv`, `zprofile`, `zshrc`, `zlogin`, `zlogout`, `profile`, `bashrc`; in the home folder `.zshenv`, `.zprofile`, `.zshrc`, `.zlogin`, `.zlogout`, `.bash_profile`, `.bash_login`, `.profile`, `.bashrc`, `.bash_logout` |
| `ssh access file` | `~/.ssh/config`, `authorized_keys`, `rc`; `/etc/ssh/ssh_config`, `sshd_config` and their `.d` folders |
| `authentication module` | every entry in `/etc/pam.d`, `/usr/local/etc/pam.d`, `/usr/local/lib/pam` and `/Library/Security/SecurityAgentPlugins`; `/etc/pam.conf`, `/usr/local/etc/pam.conf` |
| `git hook` | every entry in each checkout's `.git/hooks`, except Git's `.sample` files; the hooks in the folder Git's `core.hooksPath` names |

Never a private key, never known hosts. `.git/hooks` is read in every checkout, whatever Git's configuration says. When `core.hooksPath` names a folder, Immunity Core also reads from it the hooks named in [githooks(5)](https://git-scm.com/docs/githooks). A relative path starts at the working tree root for ordinary hooks and at `.git` for receive-side hooks. A missing folder, a path to something that is not a folder, and `/dev/null` hold no hooks. A change to `core.hooksPath` can make a hook in the named folder start or stop being watched while the file stays on disk. The first time a run can tell the folder for a checkout, the hooks in it are kept as the baseline and told once by `watched.first-read`, since Git may have run them long before. A hook another checkout's reading already watched before the run is not new where one more checkout starts to use its folder, and the journal notes it as already watched in another checkout.

Apple Git parses its own `usr/share/git-core/gitconfig` in the developer folder `xcode-select` names, `/etc/gitconfig`, `~/.config/git/config`, `~/.gitconfig`, `.git/config` and `.git/config.worktree`, in that order. It reads `config.worktree` only as Git does: when `.git/config` has `core.repositoryformatversion` and `extensions.worktreeConfig` is on. Immunity Core gives Git bounded copies and turns off Git's own loading of configuration. Git is not run from a developer folder inside a folder macOS asks permission for. The last setting wins. Immunity Core follows `include.path` and `includeIf.*.path` itself, as deep as Git does (an included file more than 10 levels deep is refused, a missing one skipped), expanding `~/` and a path relative to the including file. It reads at most 64 configuration files for the shared files and 64 for each checkout. It does not evaluate the condition of an `includeIf`, so an `includeIf` whose file sets `core.hooksPath`, or cannot be read, leaves the folder unknown; one whose file sets nothing changes nothing. The folder is also unknown when a configuration file cannot be read or parsed or leads into a folder macOS asks permission for, when Git is not installed or is in such a folder, when more than 64 files are included, when the value uses path magic such as `:(optional)` or an expansion other than `~/`, when the repository has a separate common directory or `.git` cannot be read, and when `core.worktree` or `core.bare` moves where a relative path starts. `core.bare` and `extensions.worktreeConfig` are read only as `true`, `yes`, `on`, `1`, a key with no value, `false`, `no`, `off`, `0` or an empty value, and `core.repositoryformatversion` beside the extension only as `0` or `1`; any other value leaves the folder unknown. The reading then says why, `.git/hooks` is still read, and what was read before in the named folder is kept as it was. It is partial, or none when `.git/hooks` itself could not be read.

Immunity Core does not take `XDG_CONFIG_HOME` from its own environment, since the login job has none. Git run with a different environment (`XDG_CONFIG_HOME`, `GIT_CONFIG_*`, `-c`), or another Git with its own system file, may use a folder this reader does not know of; `.git/hooks` is read in that case too. A checkout whose `.git` is a file, including linked worktrees and submodules, keeps its hooks elsewhere, and its reading is partial. Hooks that Git's configuration defines as commands are not read.

Only the hooks count in the login window's preferences, since the rest of the file changes for other reasons. CoreFoundation parses the file, in the XML, binary or old text form. Each hook's value is encoded exactly and its checksum is `has_content` of `<file>#/<key>`: a string by its UTF-16 code units, with no conversion or normalisation, an array or dictionary element by element, any other value as CoreFoundation writes it alone in binary. The file is one unit and its hooks are entries of it. A file with no hook holds no entry. A file that is not a property list, or whose top is not a dictionary, is a failed reading with the reason. A hook whose value cannot be read is named as `<file>#/<key>` with the reason: one nested deeper than 32 levels, or larger than this version reads, more than 10,000 values or 1 MiB encoded, each value counted every time it is referred to. The other hook is still compared, what was known of the unread one is kept, and losing sight of it is judged as the part's own, so that losing sight of the whole file later is found too. The public name adds the part after `#`; the baseline keeps the physical path and part separate. A literal file and a selected part with the same public name can still share an entity ID across readers. A hook, PAM file or plugins folder read before that is there and cannot be read now is a finding of its rule, with the reason, and is never told as removed. The PAM places are where OpenPAM, as Apple builds it, looks for a policy and for a module named without a path (pam.conf(5) and Apple's OpenPAM source). `/usr/lib/pam` and `/usr/share/pam.d` are left out because only an update of macOS can change them. An authorization plugin is a bundle: Immunity Core sees it arrive and go, and does not see a change inside it. The pages say so of each one instead of when it last changed, `immunity status` counts such entries per kind (`presence_only`, with `presence_only_note`), and `immunity finding <id>` says it of a finding about one. An entry the latest check did not read in full is shown as not read at the last check, with why, never as unchanged.

Not read: `ZDOTDIR`, fish, files pulled in by `Include` in the SSH configuration, other ways the Git configuration runs code. These places of persistence are left out, and `cannot_judge` and `not_covered` name them:

- login and logout hooks in root's preferences, `/var/root/Library/Preferences/com.apple.loginwindow.plist`, where `sudo defaults write` puts them; only root can read the file;
- login and logout hooks in ByHost preferences, `~/Library/Preferences/ByHost/com.apple.loginwindow.<host>.plist`, kept for one Mac;
- login and logout hooks in Managed Preferences, `/Library/Managed Preferences`, which a device management profile writes;
- a PAM policy a device management profile installs, which OpenPAM reads before `/etc/pam.d`;
- the authorization database, which says which authorization plugins run;
- the sudoers file and its folder, which only root can read;
- login items and background items, whose database needs Full Disk Access;
- crontabs, which only root can read. Listing one is a tool's output, and no documentation says that listing it raises no permission dialog;
- launchd jobs with no file on disk, which only launchd itself could list;
- the applications reopened at login, which macOS rewrites at every logout.

StartupItems and periodic scripts are not watched because current macOS no longer runs them: SystemStarter, which ran StartupItems, was removed in OS X 10.10, and `periodic` in macOS 15.

## What runs by itself

One table of data, `POINTS` in `src/autorun.rs`, holds every autorun point: the watched places above and one row per known way a file makes a tool run code on a routine action, with where the file is, which part counts, the trigger, the tool, whether the tool asks first, the ATT&CK technique, both levels, and the source the row rests on. There are 41 ways in a project and 11 places in the home folder.

Every row names where it was taken from: the tool's or Apple's documentation, a manual page, an ATT&CK technique, or KnockKnock's category. Six watched places have no source the repository can establish and say so with an empty one: `~/.ssh/config`, `~/.ssh/rc`, `/etc/ssh/ssh_config`, `/etc/ssh/sshd_config` and their two `.d` folders; so does the row of `.nvim.lua`, `.nvimrc` and `.exrc`. Every row also names the major versions of macOS its behaviour was checked on. No row is marked checked yet: none has a record of such a check. Given the running version, which `/usr/bin/sw_vers -productVersion` gives, the table answers which rows were not checked on it; a version that cannot be read is never one a row was checked on.

What an earlier run read and this version has no row for, a kind no row reads any more or a file or key a row no longer lists, is closed by the next full reading as `retired`, with why: never counted as watched, never told as removed, and said once by the run, in its text and its line on the pages, with how many facts were set aside. A watcher's first reading of every place closes them the same way when it comes before the run, and the next run says them; `last_finished_run.set_aside` in the status counts the facts set aside since the check before, by the check or by a watcher in between. Each one present is recorded as `holds_autorun_point` on its checkout, or on the machine for the home folder, whether it is read or not. The ones present and not read are named in the readings `other ways a checkout runs code by itself` and `other places in the home folder where a tool's settings run code by itself`, and the status says how many of the known ways this version reads. What is recorded of a checkout that the store still holds and a check did not look into is kept. The reading `ways a checkout runs code by itself, as present in each` is then not full and says why: the walk could not open or list a folder, or known checkouts were not looked into. The reading `other ways a checkout runs code by itself` is not full either; when a way it does not read is present, it names those ways with the cause `no_reader` instead of the walk's reason. The projects on this Mac were all found only when the latest reading of each reader that finds them, the walk of the home folder and the sessions of Claude Code and Codex CLI, was full and every folder macOS protects was entered. Until the first reading is full and the projects were all found, the status adds to its count of the ways not read, none or more, that not every project was looked at and why, and the page's table of ways shows `Not known` where no project is known to hold a way.

Immunity Core checks both pnpm filenames at every known checkout root. It records the file's presence and digest without running its code or resolving which file pnpm would load. Coverage is limited to those two paths per checkout. That leaves out hooks in workspace packages without their own tracked checkout, including packages with separate lockfiles (`sharedWorkspaceLockfile: false`), and other files configured through `pnpmfile`, `globalPnpmfile` or config dependencies. See the [pnpm hook documentation](https://pnpm.io/pnpmfile).

Each checkout row reports coverage across the known checkouts. A check that skips a known checkout or cannot complete its walk leaves the row incomplete. The store keeps the last digest of any file in a skipped checkout.

Read in the home folder (7 of 11): Claude Code's `~/.claude/settings.json` and `~/.claude.json`, Claude Desktop's `claude_desktop_config.json`, Cursor's `~/.cursor/mcp.json` and `~/.cursor/hooks.json`, Gemini CLI's `~/.gemini/settings.json` (all `autorun.agent-settings`), and VS Code's extensions in `~/.vscode/extensions`, each by publisher and name (`autorun.editor-extension`). Named and not read: Claude Code's skills, commands and agents, Continue, Codex, JetBrains plugins.

How a part is taken. In a JSON file, per selected key, the SHA-256 of the canonical value there, kept as `has_content` of `<file>#<JSON pointer>`. Strict JSON is parsed with `serde_json`, JSON with comments with the `jsonc-parser` crate, which keeps every equal key. A file with a byte-order mark, one where equal keys could be read differently at a selected key, or one not in its row's format is hashed whole, and the reading says why. A project file over 1 MiB, a home file over 32 MiB, a file that cannot be read, and a task file that cannot be parsed are failed readings with the reason. The text of a script or command is never kept.

Every row read is watched live, except `~/.claude.json`, which its tool rewrites constantly, and `*.code-workspace`, which has no fixed name; those two are read at each full check. What a row finds is judged as the lifecycle says. A part that appears where an earlier reading read or listed is a finding, and so is everything in a checkout new to a folder an earlier walk listed, such as a clone made after the first check. In the store's first full check, what is found is the baseline. A place read for the first time later, such as a project outside the folders the walk enters, becomes its baseline too and is told once, by `watched.first-read`, with how many things it holds. A file read before that is there and cannot be read now is a finding of its row, with the reason. The exception is a new linked worktree of a repository the store already holds a checkout of. There, a part equal to the one at the same path in that checkout raises nothing; it is recorded, and the journal says which checkout it matched. See [how-it-works.md](how-it-works.md#lifecycle).

## Commands

Every command except `immunity servers`, `immunity view` and `immunity watch` answers with one message of the contract, and fails with the message `Failure` (see [the contract](#the-contract)). `immunity servers` and `immunity view` print text for a person, and `immunity watch` prints its own JSON lines. Commands that accept `--store <path>` can use another store.

A command that only reads the store opens it read-only and creates nothing next to it. When a check or a watcher was killed in the middle of a write, the first such command rolls that unfinished write back, as SQLite does for any writer, so the store holds what was last committed, and then reads. Where it cannot write in the store's folder it leaves the store as it is and fails with exit 3 until a check or a watcher opens the store.

| 2 | a misuse or an unknown id |
| 3 | an unreadable store |
| 4 | a check holds the store; ask again |
| 5 | another watcher has the store: `immunity watch` |

In every answer, `title`, `meaning` and `advice` are Immunity Core's fixed words. Anything taken from the machine or a feed is only in a field whose name ends in `_text`.

The text of `immunity status`, `immunity findings`, `immunity finding <id>` and the answers to a finding depends on where it goes. When standard output is a terminal, lines fit its width (80 columns when it does not say), a table cuts only the columns that may be cut, with `…` (a path keeps its start and end, a sentence its start), a long value beside its label is broken into lines and never cut, times read as "3 min ago" up to an hour, "2 h ago" up to a day, then "16 Nov 05:44" in local time, and colour marks levels, failures and commands. Text from a source is escaped before it is measured, cut, broken into lines or coloured, so it can never start or end a colour, and it is never at the start of a line, so it cannot pass for a line of Immunity Core's own. The other commands print the same text wherever it goes.

`immunity finding <id>` prints, in this order: the level, `urgent` when it is, the short title and the id; where the thing is and the finding's state; what it is, what it means and what to do; the evidence of its kind, each fact beside its label (a program start as its program, command line, folder, what started it, signer and pid, one to a line), with events that differ only in their times and process ids shown as one, headed with how many times and the first and the last, and their process ids on one line; the response layer's verdicts, each with the core's sentence that the event was not read again when the verdict came after its line left the event log, and the person's answer, when there are any; the rule, the confidence and the ATT&CK technique on one line; and the commands that apply to its state, `seen` and `expected` for an open finding and `reopen` for an answered one, each also with `--with` when the response layer has a finding about the same thing. The journal entries it rests on are in `--json` and `--proto` only. An answer prints one line that says what was marked (`✓ Marked f9fba25172a expected until 30 Nov 05:44`), what the answer does, the reason, and the command that takes it back. A refusal is told as below.

A refusal or a failure for a person is one error on standard error, by the same rules asked of standard error:

```
error: expected needs a reason
  immunity finding f0123456789 expected --reason <text>
```

The first line is `error:`, red and bold on a terminal, and the cause in Immunity Core's words. The indented lines say what to do: for a misuse, the command as it was typed in its right form, with its own values kept and the missing part shown as a placeholder, its words in one order whatever order they were typed in: the command's own words, then its flags, then `--store`, then the form. Then, under a label, what the failure quotes, such as a path or what the system said, escaped. A line that goes on is indented, so only the first line of an error starts at the left edge. The whole usage is printed only for `--help`. No command, or a word that is not one, also lists the commands, one line each. With `--json` or `--proto` the failure is the message `Failure` on stdout and nothing is on stderr. A store that is not there, and one an older or a newer build made, are worded the same way by every command, whatever its exit code.

## The contract

A program that runs Immunity Core, such as the response layer, reads the commands of the contract. Their messages are defined by a protobuf schema in `contract/immunity/v1/`, package `immunity.v1`. The Rust types are generated from it into `contract/src/immunity.v1.rs`, which is committed. A test generates the file again and fails when the two differ, so a build needs neither `protoc` nor a generator.

The types are the crate `immunity-contract`, in `contract/`, a member of the same Cargo workspace as the core. The core prints its messages with this crate, and a program in Rust reads them with it. The crate holds the generated types and the code their JSON needs, and nothing of the core. It depends on `prost` and `serde` alone, and re-exports `prost`, so a reader decodes with the same version the types were derived with. It is not published. A program depends on it by a git path at a commit, and brings its own JSON parser:

```toml
[dependencies]
immunity-contract = { git = "https://github.com/nuanu-ai/immunity-core", rev = "<commit>" }
serde_json = "1"
```

```rust
use immunity_contract::{prost::Message, v1};

let known = v1::Known::decode(out.stdout.as_slice())?;        // immunity project <path> --proto
let known: v1::Known = serde_json::from_slice(&out.stdout)?;  // immunity project <path> --json
```

The crate's version follows the contract. Its major version is the `format` the messages carry, 1 for package `immunity.v1`. Within version 1 the schema is only added to, and each change that adds to it raises the minor version, so a reader built on an older 1.x reads what a newer core prints. A value or a field the core no longer gives is reserved by its number and its name and never used again, and its retirement raises the minor version too. A change that leaves the messages as they are, such as a comment in the schema, raises the patch version. Version 2 of the contract is a new package, `immunity.v2`, with `format` 2, and major version 2 of the crate.

A command of the contract answers with one message, in one of three forms: binary protobuf with `--proto`, the same message as one line of JSON with `--json`, and with neither, text for a person rendered from that message alone, so a person, an agent and a program are given the same thing. Text from a source is set in quotes or a column of its own, escaped as in the message. A program names its form on every call. Naming both flags is a misuse and returns a JSON failure. `immunity verdict` reads a message, which is not typed as text, so without a form it is refused. The binary form is standard protobuf, and a program in another language reads that. The JSON is Immunity Core's own and is not protobuf's JSON mapping. The generated types print it. Field names are the schema's, an enum is the name of its value without the enum's prefix and in lower case (`CAUSE_NOT_GIVEN` prints as `not_given`, the store's own word), a 64-bit number is a JSON number, and an absent optional field is null. Times are seconds since the epoch, UTC, in fields ending in `_at`.

A failure to answer is the message `Failure` in `common.proto`, and a reader checks the exit code, the ones above, before it parses. With `--proto` the binary `Failure` is on stdout, with `--json` the same as JSON, and for a person it is on stderr with nothing on stdout. It has `operation`, `ok` (always false) and `errors`, each with a stable `code`, the core's `message`, an `example` of a right call where there is one, `detail_text`, what the failure quotes (null when nothing), and `ids_text`, the ids a question fits when it fits several. `Failure` has no `format`, and its fields are numbered from 1000, which every answer reserves, so one read as any answer, in binary or JSON, reads format 0 and the reader stops.

An enum value a reader does not know, and the value `unspecified`, are read as the unsafe case, which the schema names for each enum: for `Presence` not known, for `Completeness` not full, for `Cause` failed, for `FindingState` open, for a severity and for a rule's level the highest level and for a confidence the lowest (a finding's `severity` is absent when the core cannot say, and a reader built before it could be absent reads it as `unspecified`), for `AnswerKind` no answer, for `Via` not known who gave it, for `Change` changed, and for `VerdictKind` no verdict. The generated types read a word they do not know as `unspecified`, so a value added within version 1 does not break an older reader.

Every command except `immunity servers`, `immunity view` and `immunity watch` uses the contract. `immunity status` and `immunity run` print `Status`, and `immunity sample` prints `Sample`, in `status.proto`. `immunity on` and `immunity off` print `Service`, in `service.proto`. `immunity rules` prints `Rules`, and `immunity rules --over-log` prints `Replay`, in `rules.proto`. `immunity vulnerabilities` and `immunity vulnerability` print `Vulnerabilities` and `Vulnerability`. `immunity owner` prints `Statements`, or `StatementMade` for a statement made or withdrawn, in `owner.proto`. `immunity project`, `immunity program` and `immunity machine` each print `Known`, about a project, a program or a machine. `immunity matches` prints `Matches`. `immunity findings` prints `Findings`; `immunity finding <id>` and an answer to it print `Finding`. `immunity verdict` reads `Verdict` and prints `VerdictRecorded`, both in `verdict.proto`. The types every message shares are in `common.proto`, and the event a rule matched is in `event.proto`. A map of the report by name is a list of pairs, such as `Count`, a `name` and a `count`.

Every message read from a store carries `store_id`, the id of that store; `Service` reads none and has no `store_id`: `immunity off` only adds `turned_off`, with the time alone, to the journal of the default store when one of this build's format is there, and `immunity on` adds nothing; the job's watcher, `immunity watch --background`, adds `turned_on` at its first reading after it, once for each turning on. A run, and a watcher started without `--background`, add none. `immunity off` never makes a store and never fails for want of one; `not_recorded` then says why nothing was written: `no_store`, `store_refused` (another format, damaged, not a store, or not writable; left as it is) or `busy` (a check held the store). Since 1.20.0. A finding's id is unique only within one store: a store deleted and made again can give the same id to another finding, so a reader that keeps a verdict keeps it by the store's id and the finding's id together. The id is 16 random bytes from `getentropy`, written as 32 hexadecimal characters. It is made once, when the store is made, and kept in the store's `meta` table, so it says nothing about the Mac.

### `immunity status`

`Status` is what the latest checks left: what needs a look, what is not covered, the collector, and how this Mac is watched.

In `this_mac.watched`, `how` can be `live` (within seconds while a watcher runs), `sampled` (at the watcher's sample interval), `events` (while the collector records events), or `hourly` (at each full check). Automatic hourly checks require `immunity watch --background`.

While no watcher holds the store, two fields say why. `login_job_installed` is whether the login job's property list is in `~/Library/LaunchAgents`, read from the file alone and never by asking launchd: true reads as "installed, not running", false as "not installed". It is absent for a store other than the default one, which is the job's, and when the place cannot be read. `watcher_restarting_since_at` is when the latest watcher left because the file it was started from was replaced, as an update replaces it; launchd starts the job again from the new file, and the text form says the watcher is restarting on a new core, not that it failed. It is absent once 120 seconds have passed without a new watcher. Both since 1.19.0. `turned_on_at` and `turned_off_at` are the times of the journal's latest `turned_on` and `turned_off`, and `turned_on_latest` says which of the two came last in the journal's order, never by the clock. With no watcher and `login_job_installed` false, it says how Immunity Core went off: false, by `immunity off`, said with its time; true, by something else that stopped the job or removed its property list. That state is never under a calm headline. Since 1.20.0.

`needs_a_look` lists open findings, urgent first, then the most severe, then the latest seen. It lists at most 50 of the core's findings and 50 of the response layer's, so neither source can push the other's findings out. `total` counts them all, and `urgent_total` counts the urgent ones among them all, not only those listed. Within each source urgent findings come first, so its cut never drops an urgent finding while it keeps one that is not; when a source has more urgent findings than its 50, `urgent_total` is more than the urgent ones listed. `immunity findings` lists every finding.

`needs_a_look.by_rule` counts every open finding by its rule, not only those listed: `count`, `urgent`, the worst `severity` among them, the rule's `short_title` and, for a published rule, its own title in `rule_title_text`. Rules with urgent findings come first, then the most severe, then the most findings. Since 1.16.0. The text form shows the first six and counts the rest.

A rule's `short_title` is a name of at most 44 characters for a list, beside its `title`. Immunity Core's own rules define it where the rule is defined; a published rule's finding uses its own title, in `rule_title_text`, which the text form cuts to 44 characters on a terminal. A listed finding also carries `package_text` and `releases_text` when it is about a package a lockfile declares. Since 1.16.0.

Each cause in `not_covered` says in `holds_on` where it comes from. `every_mac` is a limit of this version, the same on every Mac, such as a reader it does not have. `this_mac` was raised by a reading on this Mac, such as a failed download, a folder it did not read or software of a package manager it does not read. A cause that holds on every Mac, such as places where something runs by itself that are not read, is `this_mac` when this Mac has something there. `unspecified`, or a value a reader does not know, is read as `this_mac`, so no cause raised here is taken for a limit of the version. The text form follows it: with `--coverage`, a `nothing` cause that holds on every Mac is told under "Limits of this version", and one of this Mac under "Not judged on this Mac". The status names the places of this Mac's causes on one line, "Not judged", and puts a failed reading or download under "Failed", which is never left out.

Each cause also says in `class` what kind of gap it is, in the words of a reading's cause. `failed` is a reading or a download that was tried and did not succeed, such as a file that could not be read, a server that could not be opened or a list that could not be downloaded. `no_reader` is something this version does not read, and `not_given` is something its source does not give, such as a tool that is not installed. `class` does not depend on `who`: a failure the person can fix is still a failure. `unspecified`, or a value a reader does not know, is read as `failed`. Since 1.16.0. The text form goes by it: every `failed` cause is under "Failed", whoever can fix it, and the headline "✓ Nothing needs a look" is never shown while one is there. A download of the CISA catalogue or of an ecosystem's OSV data that failed at the last check, while the data read before is still current, raises no cause; the status still names it on a line of its own, "Downloads".

Each cause names what it is about in `examples_text`, by name only. `examples` lists the same things in the same order, each with `name_text` and `reason_text`, what its source said about it, such as why a server could not be opened. The secrets the core recognises are cut out of a reason, as in `args_text`, and `reason_text` is absent when the source said nothing. The `reason_text` of `coverage.problems` and `coverage.unreached` is cut the same way. Since 1.8.0. So are the other reasons a source gave: a cause's `value_text`, the `reason_text` of `watched.kinds`, `threats`, `vulnerability_data.feeds`, `integrity.readings` and `event_level`, and `event_level.log_cap_reason_text`.

`this_mac.fresh` says whether the answer rests on a recent check: the latest full check finished within `fresh_for_seconds` (7200) of `answered_at`. When it did not, when its time is ahead of this Mac's clock, or when no full check has finished, `fresh` is false and `stale_reason` says why. A status that is not fresh is never calm, whatever it lists; the app shows it as old, with when the last full check finished. The app also ages a status it holds: one held more than `fresh_for_seconds` after `checked_at` is shown as old in the same way. `this_mac.state` is `watched_in_part` when the collector was refused, from the start or later, failed or fell silent after it ran, and when it runs but lost part of what it was to record, of program starts or of file events where they are collected (a gap in its sequence numbers, a restart it cannot account for, lines it could not read, log files removed by the cap or left unread), in a reading the store received since the latest finished full check, that check's own reading included, or at any time when none has finished. Since the check is told by the order of the readings, never by their times. A full check that read this Mac after the loss was read and finished reads again everything installed and every place where something is set to run, so it ends that state, except for lines it could not read: those are a failed reading and keep it for the day. Every loss stays in `rules.judged`, the `last_day` counts and `in_words` for the day. Since 1.20.1.

### `immunity project`, `immunity program` and `immunity machine`

| Field | Holds |
|---|---|
| `question` | which question was asked, `project`, `program` or `machine`, so an `unknown` answer says of what kind |
| `presence` | `held` while the store has facts in force about one of the thing's ids or about what is on it; `gone` when what was read of every id is retracted and the latest reading of each reading that wrote about them was full; `unknown` when the store has never heard of the thing, or when none of its ids is held and such a reading was not full, so what it did not read again may still be there |
| `thing`, `same_as`, `parts` | the thing's entity; the other ids the store knows it by, such as a machine's names the resolver links, a Homebrew formula's kegs, or the folder of code an application keeps under `~/Library/Application Support`; and what is inside it with facts in force, one level. For a project: components `part_of` it, files `located_on` it, and files whose path is in its folder. For a machine: what is `part_of` or `located_on` it, such as its containers, packages, checkouts and watched files, without their own parts; `immunity project` gives a checkout's. A program has none |
| `facts` | the facts in force about the thing and its parts, each with the assertions it rests on: `reader`, `basis`, `source_ref_text`, `observed_at`, and the reading's scope and kind. A fact whose subject is in `same_as` is about the thing |
| `coverage` | the latest reading of each reader, scope and kind that speaks for the thing: the readings of it and its parts, those that wrote its facts, those that look for things of its kind, for a project the readings of this Mac that read inside every project, and one that names a folder macOS asks permission for that holds it. Each has `completeness`, `reason_text` (whole), `cause` and `observed_at`, and lists what it has no reader for |
| `findings` | the findings in every state, by id, with `rule`, `state`, `severity`, `confidence` and `urgent`: those about the thing under each of its ids and about anything inside it at any depth, whether what was read of it is in force or retracted. Inside means `part_of` or `located_on` the thing or one of its parts, named by its id as on the thing (a file or a checkout of a machine), or for a project an id that lies in its folder. So a machine's findings include its projects' packages and the files no reading tied to it, such as a program that ran or a place that could not be read. A finding stays in the answer after the file it is about is removed |
| `latest_run_at` | when the latest run that finished ended; absent when none has. A reading older than it was not made again in that run |

Each question answers for one type of entity: `immunity project` for a `checkout`, `immunity program` for a `component` or a keg's `file` that a reading of installed programs wrote about, and `immunity machine` for a `machine`. An id the store holds of another type is refused with `not_a_project`, `not_a_program` or `not_a_machine`, exit code 2. No question answers for a watched file by itself: a `file:` id given to `immunity project` or `immunity program` is the path it names, and answers for the project or the program that holds it.

The readings that look for things of a kind are, for projects, the walk of the home folder and the reading of agent working folders, given with every project; for programs, the `integrity` readings of application bundles, Homebrew kegs and global npm packages and the `brew` reading; for machines, the `ssh-config`, `known-hosts` and `tailnet` readings. A program or a machine the store has never heard of carries all of its kind. A known one carries those that wrote about it. A project the store knows also carries the readings of this Mac that look inside every project, the ones of the table of ways a project runs code by itself, since one that is not full may be about this project.

A thing the store has never heard of is `unknown`, and its coverage shows which readings looked for it. In a thing that is known and read in full, every reading is `full`. A project in a folder macOS asks permission for keeps what was read there before, and its answer carries the reading `folders macOS asks permission for` with completeness `none`, naming that folder. So does a program path in such a folder. A program whose reading could not read all of it, such as a package whose manifest links into such a folder, carries that reading as `partial`. A server whose sweep did not complete carries its readings as `none`.

Four readings are made by rule rather than read from the store. Each has completeness `none` and no `observed_at`, and nothing like them is kept in the store. The first three have the cause `not_given`:

- A machine other than this Mac that the server check never visited, under any of the ids the resolver links: `servers`, `sweep visit`.
- A machine the owner set aside as retired or not theirs: `servers`, `sweep of a machine set aside by the owner`. Its reason names what the owner said and the day, and nothing of the owner's reason. `immunity owner --json` lists the statements that stand.
- A path that is not judged on its own: `immunity`, `places the readings that find projects look in` (or programs), scoped to this Mac, its reason saying why. A path under no project or program the store holds is answered `unknown`: the store does not keep where its readings looked, so such a path never reads as looked at, and never as `gone`. A folder that holds some without being one, such as `~/Library/Application Support`, a Cellar, the home folder or `/`, is answered `unknown` too, says how many it holds, and holds the findings about anything in it. A path strictly inside one, such as a file in a bundle or a settings file in a folder of code, answers for it: a reading compares a project or a program as a whole and does not keep which paths inside it compared. So does a path the store holds only in another case or Unicode form.
- A program the store never heard of, answered `unknown` by `immunity program`: `immunity`, `software of package managers this version does not look for`, cause `no_reader`. Its reason is the limit that a package manager other than Homebrew and npm is not read, and that Homebrew or Tailscale installed outside their default places is not found.

A path inside a project the store knows, held or gone, answers for that project, the nearest one that holds it, with `asked_text` the path as asked. A path that names no project as written is followed through symbolic links one part at a time, and never inside a folder macOS asks permission for; a link into such a folder answers `unknown` with the reading that names it.

Every command that takes a path or a `file:` or `checkout:` id puts it into one form first: `..`, `.`, doubled and trailing slashes are resolved by the words alone, in an id as in a path, a slash after `~/` stays in the home folder, and no link is followed. What is asked is compared as written first and then by its key, in case and Unicode form: a path, the machine an id names, a program's name or id. A match by the key alone answers for what the store holds, with the reading made by rule that says it is spelled otherwise: the Mac's volumes ignore both by default, and the disk is not asked. A machine's id is compared as its name is, so `machine:<name>` fits as `<name>` does. Findings are gathered by the same comparison, so an answer holds every finding the store has about the place asked, the thing that holds it and anything inside it, however the place was spelled.

`immunity program` takes a path to the program whose folder holds it: the path in its `installed_at`, or the path a keg's id names. A path at or inside a folder of code the store holds or held, or that folder's id, takes the application it belongs to. A program that moved, or one of two copies of it that went away, is still the program at the folder it left, unless another program is there now. A program's id is that program, and a `file:` id of this Mac is the path it names. Anything else is a name, matched against the last part of a program's id, `component:<machine>/<ecosystem>/<name>`, or against the formula a keg's path names. One program can be known under ids that no fact links: a Homebrew formula and its kegs, tied by the formula's name (the last part of Homebrew's name for it) and a version Homebrew gave for that formula, and an application and the folder of code it keeps under `~/Library/Application Support`, tied by its bundle identifier or its folder's name as the `integrity` reading matches them. The tie runs from a program to its own parts and no further, so two applications that match one folder, or two formulas of one short name, stay two programs. A program is `held` while any of its ids is. The `integrity` reading opens every folder of code it holds or held whenever the folder is there, even after its application was removed or moved out of the two Applications folders. It keeps the version the application last had and names the folder in its note. A folder that comes back after a reading missed it is read as for the first time and compared from then on. Once its application is not read, a folder with no code file left, such as one an uninstaller left with a settings file, is let go, and the application can be `gone`. Such an application is `held`, and a change to that code raises `integrity.app-code-outside`. Of two applications that match one folder, the store does not keep which one the reading matched it to, so both are `held` while the folder is. Asked by any of these, by every id in `same_as` or by a path inside any of them, the answer names the thing asked and lists the others in `same_as`, with their facts, readings and findings. Its findings include those about anything in a folder where one of them is or was installed, so the answer by name, by id and by path hold the same.

A question that fits more than one thing fails and names each of them. A name that fits two programs, such as a formula and a global npm package called the same, fails with `several_programs`; a name that fits machines not known to be one fails with `several_machines`. Both exit with code 2 and list every id the question fits, whole, in the error's `ids_text`, so each can be asked again.

The text for a person follows the status. Its first line is the kind of thing and the thing as asked, with the time of the latest check; the next says whether it is there and how many of its findings need a look, how many of them urgent. A reading made by rule about what was asked comes right after, in the core's words. Then the open findings by rule under their short titles, each with its ids when there are three or fewer, and the store's facts in a person's words: where it is, its version, the packages or programs inside it, the files they were declared in. The count of readings always says how many are not full, and each one not full is listed with its reason. A presence of `unknown` with a thing is said as "cannot tell whether it is there now", never as gone.

As in every other answer, text from the Mac is only in fields ending in `_text`. Entity ids are such text, since they hold paths and names from the Mac. An entity id is opaque: compare it whole and never take it apart. In the contract's text a hidden character is written `\u{...}` and so is the backslash itself, `\u{5c}`, so no two texts are shown alike. An id or a path given to a question is read the same way, so every id an answer prints asks back the same thing, and a path with a backslash in it is written with `\u{5c}`. These answers cut no text: an id, the place a fact was read and a coverage reason are given whole, so they can be matched and asked about again.

### `immunity findings` and `immunity finding <id>`

The response layer gives a verdict about a finding, so it reads one whole. Both answers read the same findings as the status and the pages, in the same order: urgent first, then the most severe, then the latest seen, then by id. A finding of a rule this build does not have is in every answer, as it is everywhere else. Its `kind` is `finding of a rule not in this version`, `finding.rule` is the rule the store keeps, and `severity` and `confidence` are absent, since the store keeps no levels without the rule. It is not urgent, and it is ordered as the most severe after the urgent findings.

`Findings` lists every finding the store holds, in every state, each as its reference (`finding`: `id`, `rule`, `about_text`, `state`, `severity`, `confidence`, `urgent`) with `kind`, `kind_title`, `title`, `where_text`, `thing`, `first_seen_at`, `last_seen_at`, the person's `answer` and `verdicts`, what the response layer said about it, counted (see [`immunity verdict`](#immunity-verdict)). `latest_run_at` is absent when no full check has finished. The text says so and lists any findings already recorded. `--all` changes only the text for a person; the message carries every state either way.

`Finding` is one finding whole:

| Field | Holds |
|---|---|
| `finding` | its reference, as in the list |
| `kind`, `title`, `meaning`, `advice` | the core's own words, the same for every finding of its rule |
| `kind_title` | `kind` as a person reads it, a short title such as `Shell startup file` for `shell profile`, as the pages show it. Match on `kind` |
| `technique_text` | the ATT&CK technique its rule names, or the first of a published rule's tags; absent when none fits |
| `where_text` | where the thing is, as a person recognises it |
| `thing` | what it is about in the core's words, when no name from the Mac says it. Only `watched.first-read` has it: the places its check read for the first time, counted by kind, such as `2 projects and 1 other place`. `where_text` is then the machine |
| `first_seen_at`, `last_seen_at` | when it was first found and when last |
| `answer` | the person's answer: `given` (`expected` or `seen`), `via` (`app`, `agent`, `command`, or `unknown` for one given before this was kept), `given_at`, `reason_text` with the secrets Immunity Core recognises cut out, each a mark (see [Secrets](#secrets-in-what-immunity-core-keeps-and-prints)), `until_at` for `expected`, and `in_force`, whether it hides the finding now. Absent when there is none, including after it was taken back |
| `evidence` | one key, the kind of finding, holding what it rests on beside the journal |
| `rests_on` | the journal entries it rests on, oldest first: `seq`, `recorded_at`, `run_id`, `entry`, `reader`, `kind`, `predicate`, `subject_text`, and the value before and after, `old_value_text` and `new_value_text` |

For a person, a refusal of an answer gives the command to run next made from the one typed: the finding read again, the answer taken back, the same command with `<id>` for the other finding of a pair, or `immunity findings --all` when the id is not known.

`immunity finding <id> expected`, `seen` and `reopen` answer with `Finding`, the finding as the answer left it, in the form asked.

#### One answer for a pair

A rule's finding on this Mac can have a second finding beside it: the response layer's `verdict.suspicious` finding of that rule about the same thing (see [`immunity verdict`](#immunity-verdict)). `--with <id>` gives one answer to both. It names the other finding of the pair. For a finding of the core that is the `verdict.suspicious` finding of its rule about the same thing, which its `verdicts.verdict_finding` names while one is open or expected. For a `verdict.suspicious` finding it is the core's finding of that rule and thing. The caller always names it. An answer never reaches a finding the command did not name, and a linked finding is never answered by default.

The pair is checked by rule and thing, not by occurrence. Any occurrence of the other finding passes that check, and each answer then refuses a finding it cannot answer: `seen` and `expected` one that is not open or expected, `reopen` one with no answer. An occurrence the command did not name is never changed.

The two answers are one transaction: both are recorded or neither is. Each finding keeps its own answer with the same kind, reason, `--days`, `--via` and time, as if it had been answered alone, so the status, `immunity finding`, the pages and taking an answer back all read two ordinary answers. The journal records an entry for each, under one run id. `reopen --with` takes both answers back in the same way, and `reopen` without it takes back only the finding it names. The answer is the `Finding` named first, with `answered_with`, the other finding's reference and its state after the answer (since 1.9.0). It is read in the same transaction before the commit, so a command that is refused has recorded nothing. A third finding about the same thing, of another rule or another occurrence, is never touched. A finding of a rule this build does not have is answered like any other, with or without `--with`.

A later verdict is not answered in advance. After `seen`, the next `suspicious` verdict about the same rule and thing raises the next occurrence of the response layer's finding, open and urgent by the ordinary rule. After `expected`, that finding stays expected until the mark ends.

An answer is tied to what the caller read, as an HTTP request is with `If-Match`. `Finding`, `Findings` and `Status` carry `journal_seq`, the journal's latest sequence number in the state of the store the answer was read from (since 1.9.0). `--journal-seq <n>` passes it back. The answer is refused with `changed_since_read` when, after that entry, one of these joined a finding it answers: a match of its published rule; a newer reading it rests on, as when a lockfile's finding is found again with newer data; a verdict that went to it, raised it or names it; an answer given to it or taken back; its clearing; or the end of an `expected` mark once a check records it, which the clock alone does not. A rule's finding shows the response layer's `verdict.suspicious` finding of its rule about the same thing inside its own message (`verdicts.verdict_finding`), so the same check covers that finding too, one raised after the read included, and `detail_text` then names it. Nothing else refuses: a newer occurrence of the same rule does not refuse taking back an older one's answer, which quiets nothing. Each of these writes a journal entry in the transaction that makes it, and the journal's numbers only grow, so the check goes by when the store learned of a thing, not when it happened, and misses nothing recorded after the read. Every reading in which a published rule matches writes a `matched` entry with the rule, and the check finds the later ones by the rule; the finding still rests on the one that raised it. What refuses depends on the answer. `seen` says the person looked at what is there, so anything that joined since refuses it. `expected` says more of this is expected, and by its meaning already quiets every later match of the rule until the mark ends. A match of the finding's own rule between the read and the answer is no different from one a second after it, so it does not refuse `expected`. A verdict is another party's statement about the thing and still refuses it, as does everything else in the list. `reopen` is checked as `seen` is. So a finding of a rule that keeps matching can always be marked expected, while `seen` may keep being refused for as long as it matches. One number covers every finding in the store. When the two findings were read in two answers, pass the smaller `journal_seq`. `--journal-seq` is required on `seen` and `expected` given with `--with`, with `--via agent` or with `--via app`: the app passes the `journal_seq` of the message the person answered on, the opened `Finding` or the `Status`. From the command line without `--via` it is optional, and honoured when given. `reopen` needs none, since taking an answer back quiets nothing, but honours one given.

Nothing is recorded when the command is refused. A refusal about the finding named by `--with` quotes its id in `detail_text`:

| Code | Exit | When |
|---|---|---|
| `not_the_pair` | 2 | the finding named by `--with` is not the other finding of the pair: it is of another rule, about another thing, or the same finding twice |
| `unknown_finding` | 2 | the store has no finding with that id that this build shows |
| `finding_closed` | 2 | either finding is not open or expected, so `seen` or `expected` has nothing to answer on it |
| `finding_not_answered` | 2 | either finding has no answer for `reopen` to take back |
| `changed_since_read` | 2 | something joined a finding after the read `--journal-seq` names; `detail_text` is the id of the first that changed. A match of the finding's own rule does not refuse `expected`. Read again, show the person what is new, and answer with the new `journal_seq` |
| `journal_seq_ahead` | 2 | `--journal-seq` names an entry the store's journal has not reached, so it was not read from this store |
| `usage` | 2 | `--with` or `--journal-seq` without an answer, given twice or empty, or `seen` or `expected` with `--with`, `--via agent` or `--via app` and without `--journal-seq` |
| `store_unreadable` | 3 | there is no store, or it cannot be read |

### `immunity matches`

The response layer looks into what the core is not sure of. `immunity matches` gives it every match of every published rule, of every level and with none, each with the event it matched, in the order of the log; events that matched no rule are left out. The store keeps no event and no match, so the command reads the collector's log again and evaluates each event with the same code the core's own reading uses: the two never disagree about what matched.

The caller keeps its place. Each answer prints one in `continue_after`, and `--after` takes it back to read on from there; without `--after` the answer starts at the oldest line kept. A place is the core's own words: a string of lower-case hexadecimal that a reader stores and passes back whole, and never parses or compares. It holds what the core's own reading keeps for itself: for each log file, its identity (the run and start its name gives, or an earlier collector's hour, and its inode), how far it was read, and whether it was over when it was read to its end, together with the last number `eslogger` gave each kind of event and the filter's markers no gap has taken in yet. A place for a day of 25 files is about 730 characters. `--after` takes only the places this build prints, checked character by character and number by number. Anything else, a place an earlier build printed among them, is refused as a misuse with exit code 2, and `immunity matches` without `--after` starts again from the oldest line kept. A place names no path: a file is only ever looked up among the files the log folder lists.

Reading on from a place works the way the core's own reading works. A file the place holds, with the same inode, is read on from where the place left it. Any other file is read from its start, whatever its name: one the place does not hold, one of the same name with another inode, and one shorter than the place's offset. A file the place holds that is gone or was replaced had lines the place did not read when the collector's note of its deletion says it held more, or, with no note, when the place had not read it to the end once it was over, that is once a later file had been written to. The answer then says `gone`. Nothing is skipped without the answer saying so. An event may be given twice, after a file was replaced, and is never missed. This holds for a clock set ahead and back, a reinstall within one hour, and a file deleted before it was read.

| Field | Holds |
|---|---|
| `matches` | each match with `position`, `rule` (`name`, `file`, `id_text`, `title_text`, `level`, `techniques_text`, `author_text`, `source`, `set`), `event`, `raised`, `findings` and `verdicts`, the response layer's verdicts about that match, counted and listed as for a finding. After the findings the core's reading recorded, `findings` names the `verdict.suspicious` finding of the latest `suspicious` verdict about the match. A match is named by its position and its rule's `name`, its set and its id, `sigma:<id>`, `elastic:<id>` or `elastic-behaviour:<id>`, the same in every command, which a finding of a set that raises carries; `source` and `set` give the set by name and in words; `file` is the path under that set's folder, `rules/sigma/`, `rules/elastic/` or `rules/elastic-behaviour/`. `level` is `not_stated` for a rule whose set states none, Elastic's behaviour rules: a value that is not a severity. A reader built before it was added reads it as a value it does not know, so as the highest level; a rule's level never decides whether the core raised a finding, which `raised` says. Positions are not ordered as text: matches come in the order of the log |

A line did not give a group when it lacks the group's key, as an earlier collector's lines do, so the rule was not asked about it; for `identity` and `signature`, which every process has, also when it carries the key with no value. Most program starts run no script, so a start with the script's key and no value is not counted. Every one of Elastic's detection and behaviour rules for macOS that the translation did not take is here too, by its upstream file and `name`, with the translation's reason, `sequence`, `not_eql`, `needs_events`, `needs_fields`, `backslash_in_wildcard`, `spans_kinds`, `never_true`, `regex`, `unsupported` or `function`, and what the translation said of it in `detail_text`. An answer with no matches says that nothing matched only when `collector.state` is `running`, the stretch shows nothing lost, unreadable or gone, `collector.file_events_collected` is true, and no rule the reader cares about is in `unevaluated`. Quiet rests on `unevaluated`, which covers the lines the answer read, and not on the lists of what arrives in `collector`, which are the core's latest reading and may be older than those lines. A group that only some lines fill by nature, as `script` is, is judged by the core's latest reading alone: one start without a script cannot tell a program that runs none from a field the collector stopped filling. After the collector stops filling such a group, an answer over lines the core has not read yet can stay quiet until the core's reading has counted the group's bound, 1,000 program starts for `script`, and for as long as the core does not read at all. No shipped rule reads such a group. A rule listed `in_part` is evaluated, so a match of it is a match, but the absence of one says nothing about the alternatives that need the fields in its `fields_text`. The values of `raised`, `collector.state`, `unevaluated.reason`, `action` and a rule's `level`, and the kinds of event, will grow within version 1. A reader treats a value it does not know as something it cannot judge, and a rule's level it does not know as the highest, which never says whether a finding was raised.

Which finding a high match went to is recorded when the core's own reading reads the line: the line's file, inode and offset, the rule and the finding. Only matches of rules marked high or critical are recorded, since only they raise a finding. A row goes when its log file is no longer there. `not_read_yet` is not a promise: a line deleted before the core's reading reaches it is never read, and no finding holds it. For `not_read_yet` and `no_finding` the reader judges the match itself.

A gap in `eslogger`'s numbering at the seam between two answers is counted in the later one, from the last numbers the place holds. Without `--after`, the first event of each kind has nothing before it, as at the start of the log.

One answer holds at most `--limit` matches, 1,000 by default. It also stops once the lines it matched come to 4 MiB in the log, since one command line can be a megabyte. On an invented busy hour, 1,000 matches were 892 KB of JSON and 398 KB of binary protobuf; twenty matched starts with half a megabyte of arguments each stopped at 8, about 4.2 MB of JSON.

Text in an event is given whole, except for the secrets cut out of its arguments, which `cuts` lists (see [Secrets](#secrets-in-what-immunity-core-keeps-and-prints)). No path is cut, each argument is a string of its own, and hidden characters are escaped as elsewhere. The environment is not in the log and not in the answer. On a Mac without the collector, the answer has no matches, the state `not_installed` and the rules for file events in `unevaluated`, and the command exits with 0. Without a store, or with one that cannot be read, the command fails with `store_unreadable` and exit code 3, as the other commands of the contract do: without the store it cannot say what became of a match. A log that cannot be read is a failure with the code `log_unreadable` and exit code 1. Every failure is the message `Failure`, so a reader that takes it for a `Matches` reads format 0 and stops.

The core cannot give these today: the parent's start time, which `eslogger` does not give in an `exec` message, so `parent` is the pid and pid version alone; and how many lines a deleted file held, so `gone` says only that lines are gone.

### `immunity verdict`

The response layer looks into a match or a finding and gives the core a verdict: `suspicious`, a person should see it, or `harmless`. `immunity verdict` reads exactly one `Verdict` on standard input, binary protobuf with `--proto` and JSON with `--json`, records it, and prints `VerdictRecorded` in the same form. Standard input that is a terminal is refused: the command asks nothing. A verdict over 65,536 bytes is refused, never cut. What this build does not read is refused in either form: a field the schema does not name, at the top or inside `match` or `finding`, a field given twice, or both `match` and `finding`. A binary verdict must be the encoding this build gives the same message.

| Field of `Verdict` | Holds |
|---|---|
| `format` | 1 |
| `store_id` | the `store_id` of the answer the response layer judged; another store's is refused |
| `match` or `finding` | what it is about: a match by `position` and `rule`, both as `immunity matches` printed them, or a finding by `id` |
| `kind` | `suspicious` or `harmless` |
| `reason_text`, `case_text` | the response layer's reason, at most 1,000 Unicode scalar values, and its own reference to its case, at most 200. Each needs a visible character. Longer text is refused, never cut |
| `severity`, `confidence` | on the core's scale: required on a `suspicious` verdict and refused on a `harmless` one; a confidence is `low`, `medium` or `high` |
| `verdict_id` | optional: an id the response layer makes for this verdict, one nobody can guess, such as a UUID. A token, not text: 1 to 200 characters of printable ASCII, `!` to `~`, with no backslash. It is kept, shown and compared exactly as sent |

A verdict never writes into a finding the core raised: not its state, its occurrences, its evidence, when it was last seen, its levels or whether it is urgent.

A `suspicious` verdict is an event of one rule of Immunity Core's own, `verdict.suspicious`, and raises a finding the way any rule that finds an event does. The finding is about the rule the verdict names (the match's rule, or the rule of the finding it names) and the thing that rule's findings are about on this Mac; in the store its rule is `verdict.suspicious:<that rule>`, and in every answer its `rule` is `verdict.suspicious`, its `kind` is `verdict of the response layer`, and `value_text` is the title of the rule it is about, or, when the finding the verdict that raised it named is of a watched place that could not be read, that finding's own title, which says so. A verdict about a finding and one about a match of the same rule and thing go to the same finding. Open, it stays open as more verdicts come; marked expected, it stays so until the mark ends; marked seen, the next `suspicious` verdict raises its next occurrence. The core never clears it: only the person closes it. Its severity and confidence are the highest any verdict of its occurrence gave, so they only go up, and it is urgent by the ordinary rule. For a verdict about a match, the core reads the line at the position again under `--system-root`, evaluates its event with the same code as its own reading, and the rule must have matched it; the finding keeps that event as a rule's finding keeps events.

The log keeps about a day. When the line is no longer in it (the file its position names is gone, or another file has its name now), a `suspicious` verdict is recorded and raises its finding all the same, with no event kept, and its `RecordedVerdict` has `event_gone` true: the core did not read the event again and did not check that the rule matched it. The meaning of the finding it raises says so in the core's words, on every surface that shows it, and the text of `immunity finding <id>` and the summary page say it beside the verdict. The rule must still be one this build ships, the position one `immunity matches` prints, and the time its file's name gives a real one, not later than now. A `harmless` verdict about such a line is refused with `match_gone`.

A `harmless` verdict is a record: kept, shown beside what it is about, and nothing else.

A verdict with a `verdict_id` the store already holds, equal in what it names, its kind, its reason as kept, its case and both levels, is answered with the verdict recorded then and `already_recorded` true, whatever the state of its finding and whether or not the log still holds its line. This is decided right after the check of the store, before anything else can refuse it, and again under the write lock, so of two that send the same id at once one records and the other gets that verdict; the store holds at most one verdict for an id. Nothing is written and nothing is raised: a repeat sent after the person answered the finding gets the earlier `recorded_at` and the finding as it stands now, so a new decision needs a new id. The same id on a message that differs in any of those is refused with `verdict_id_reused`, and nothing is recorded: a verdict that is a real decision is sent again under a new id. Its `detail_text` names the fields that differ and the earlier verdict's kind and `recorded_at`, and nothing of the text of either message. A verdict with a new id is a new decision, even when the rest of it repeats an earlier one.

Between verdicts that carry no id, the same message, equal in what it names, its kind, its reason, its case and both levels, is recorded once while the finding it went to is open, and a `harmless` one is recorded once; the second answer gives the first with `already_recorded` true. After the person answered that finding, the same message is the response layer saying it again and raises the next occurrence. Each verdict is an entry `verdict` in the journal.

Verdicts are not signed, as answers are not. Anyone who can run `immunity verdict` as the person can send one, and the core cannot tell the response layer from another program doing so. A verdict about a match names a line of the log under the `--system-root` the command is given, as `immunity run` reads the log under its own, and whoever can run Immunity Core as the person can do either. That is why a verdict never writes into the core's findings.

`VerdictRecorded` has `format`, `answered_at`, `store_id`, `recorded` and `already_recorded`. A recorded verdict (`RecordedVerdict`) holds the `verdict` as sent, its text escaped as all text of the contract, `recorded_at`, `finding`, the `verdict.suspicious` finding a `suspicious` one was recorded in (absent for a `harmless` one), `raised`, whether it raised that occurrence, `event_gone`, whether its line had left the log, and `reason_cuts`, what was cut out of the reason because it held a secret, each piece with its `kind` and `length` (`argument` is 0). A reason is kept with its secrets cut, so two verdicts whose reasons differ only in a secret are the same message.

What is shown beside a finding is `Verdicts`: `total`, `suspicious`, `listed` and `verdict_finding`. An answer lists at most the first verdict and the latest 20, with the total. In `Findings`, a finding of the core lists none and names its `verdict.suspicious` finding when one is open or expected; a `verdict.suspicious` finding lists the verdict that raised its occurrence. In `immunity status --json` an item carries `verdict`: for a finding of the core, `said` (the core's words, such as "2 verdicts from the response layer, 1 suspicious."), `total`, `suspicious` and `finding`, with no text of the response layer's; for a `verdict.suspicious` finding, `said`, then the raising verdict's `reason_text`, `case_text`, `at`, `severity` and `confidence`, and `more`, how many came after it. The text of `immunity finding <id>`, the summary page and the app show the core's words first and the response layer's text after them, quoted and whole: a quote character inside it is escaped, and on the page the reason is a block of its own.

`immunity status --json` cuts what needs a look per source, in the one order: up to 50 of the core's findings and up to 50 of the response layer's, so that neither source can push the other's findings out of the list. The text form shows the first rows and says how many more there are; `immunity findings` lists every one.

A failure is the message `Failure`, in the form named. Without a form the command is refused as a misuse before it reads standard input. Nothing is recorded, and a refused verdict writes nothing to the store: a file that is not a store of this format is not made into one.

| Code | Exit | When |
|---|---|---|
| `usage` | 2 | no form is named, standard input is a terminal, or the command line is wrong |
| `too_large` | 2 | the verdict is over 65,536 bytes |
| `not_a_verdict` | 2 | it is not one `Verdict` of format 1 this build reads: it cannot be read, has a field the schema does not name or a field twice, names neither a match nor a finding or both, has no known kind, has a level that is not on the scale, lacks a level on a `suspicious` verdict, or has one on a `harmless` verdict |
| `empty_reason`, `empty_case` | 2 | `reason_text` or `case_text` has no visible character |
| `reason_too_long`, `case_too_long` | 2 | `reason_text` is over 1,000 Unicode scalar values or `case_text` over 200 |
| `verdict_id_not_a_token` | 2 | `verdict_id` is given and is not 1 to 200 characters of printable ASCII, `!` to `~`, without a backslash. `detail_text` names the field and never what it holds |
| `holds_secret` | 2 | a key of the verdict, `case_text`, `verdict_id`, `store_id` or what it names, holds a secret Immunity Core recognises. `detail_text` names the field and never what it holds. A key is never rewritten: cut, it would name something else. A secret in `reason_text` is cut, never refused |
| `secrets_unchecked` | 1 | the patterns secrets are recognised by did not load, so the verdict cannot be checked |

## Secrets in what Immunity Core keeps and prints

A command line can hold a token or a password, and what Immunity Core keeps and prints reaches the person's agent, which may send it to a model in the cloud. So Immunity Core cuts secrets out of the arguments of a program start before it keeps them as a finding's evidence and again each time it prints an event, in every command and every form. Rules are evaluated on the arguments as the log holds them, in memory, before anything is cut, so a cut never changes what a rule matches. Prose is cut the same way and never refused: what the collector printed (`said_text`), the reason a person or their agent gives with `immunity finding <id> expected|seen --reason` or `immunity owner … --reason`, and a verdict's `reason_text`. It is kept with its secrets cut, and the answer lists what was cut in `reason_cuts`, each piece with its `kind` and `length` (`argument` is 0), as every later answer that shows the reason does: `Answer`, `Statement` and `Said` since 1.7.0. Cutting always runs, so an empty list means nothing was cut. A value that is a key, such as a verdict's `case_text`, is never rewritten: one that holds a secret is refused. A failure's `message` is Immunity Core's own words and never repeats what it was asked. What it repeats goes in `detail_text`: an argument, a name asked for, a path, a key or a value sent. That field is cut where it is printed, in every form and for every command. An answer that repeats the question cuts it too, in `asked_text` and `id_text`. A reason a reader's source gave, such as why a server could not be opened or a download failed, is cut on its own before it is put beside Immunity Core's words, wherever it is shown: in `immunity status` (`watching.failed[].detail_text` too), in the line the pages show for each run, in the reasons and hints on the pages, in the lines and the "Last file" column of `immunity servers`, and in the `detail_text` of a problem `immunity watch` prints. Immunity Core never cuts a line it put together as a whole, so what one source said cannot take Immunity Core's words with it: the counts, what needs a look, the names of other places and the advice stay. A reason withheld whole becomes one mark in its own place. Immunity Core decides from the reason as the source said it, for example whether to give the advice about a host key, and the store keeps it that way. A run's line is kept as the run put it together, with its reasons cut; a line an earlier version kept is shown as it was kept. Names of places, such as a path, a file's name, a folder that could not be listed or a server's name, are not searched, and neither are a program start's path, working directory and script. A name is shown on every surface with its backslash written `\u{5c}`, so a file named like a mark never reads as one.

What is recognised:

- gitleaks's published patterns, `config/gitleaks.toml` at commit `5f6ec56cfa6f`, in `rules/secrets/gitleaks/` with its NOTICE: the 217 rules not bound to a file, with their keywords, secret group, entropy threshold and allowlists. Three example values in the allowlists are left out, so no key-shaped string stands in the repository; the NOTICE names them, and without them more is cut. Not taken: the `gitleaks:allow` comment, the decoding passes and the path allowlists.
- The value of a flag or key whose name says it is a secret, from Datadog's word list (`*password*`, `*passwd*`, `*mysql_pwd*`, `*access_token*`, `*auth_token*`, `*api_key*`, `*apikey*`, `*secret*`, `*credentials*`, `stripetoken`) and three words of Immunity Core's own (`token`, `pass`, `passphrase`), whatever its length or entropy. In a name `-`, `_` and `.` are the same character and case does not count. A word without `*` matches the whole name or its last part, so `--password`, `DB_PASSWORD=`, `db.password=` and `--github-token` all match. A name is read at the start of a word and after every `=`, `:`, `&` or `?` in it, so `--from-literal=password=`, `user=a&password=` and `?access_token=` are found too. The value comes after `=` or `:`, whatever it begins with, or as the next word or argument after a flag that has neither, where a word that begins with `-` is the next flag and never taken.
- A password in a URL, by detect-secrets' `BasicAuthDetector`, with an empty user as in `redis://:<password>@host`, up to the last `@` before the host.
- Two forms of Immunity Core's own: an `Authorization` or `Proxy-Authorization` header without quotes, as `eslogger` gives an argument, and a MySQL or MariaDB client's password joined to `-p`.

Where a value ends is decided the same way for every form of Immunity Core's own (a flag's value, an `Authorization` header, `-p`), and when unsure more is cut. When the name begins its argument, as `--password=<value>` or `DB_PASSWORD=<value>` does, the value runs to the end of that argument, spaces and all. When it stands inside a longer text, such as an `sh -c` string, the value is one shell word: quotes and backslash escapes are followed. Names are read from the same words, with their quotes taken off, so `"--password" <value>` and `'--password=<value>'` are found. From the first thing the reader does not follow exactly, no word ends before the end of the argument, and every value after it runs there: a backslash before a character no shell needs escaped, a quote never closed, and in or out of quotes a backtick, `$(`, `${`, `$[`, `$'`, `<(` and `>(`.

A mark is read the same way in every text that is cut: one Immunity Core made, and one a source quotes from what Immunity Core printed, of a kind the patterns cut, bare or with its backslash doubled as JSON writes it. A mark is a value already cut, one piece of a word and never part of a name. It covers only its own bytes and never changes how any other byte is read: the patterns read the text around it once as if the mark were a space and once as if it were not there, and both readings' cuts are taken, so a token glued to a mark is found as it would be beside a space. A value that begins with a mark ends where a real value would: at the end of the argument when its name begins the argument, otherwise at the end of its shell word. Only a value that is the mark alone, with the quotes and closers that end its word, is not cut; anything else in its reach is cut as a real value's would be. `,`, `]` and `}` end no word. A mark a source quoted is kept and shown as the source's text, with its backslash written `\u{5c}`, so it never reads back as one Immunity Core made. That holds wherever text from a source is shown: the contract, the text for a person, the pages, `immunity servers` and the lines of `immunity watch`. Only the report's JSON writes an argument's backslash bare, with the cuts listed beside it. A mark of a kind the patterns do not cut is ordinary text. A kind is exempt in the same way, and only where Immunity Core prints it in a list of cuts, as `"kind":"detect-secrets:basic-auth"`; anywhere else, as in `detect-secrets:basic-auth=<value>`, it is read like any other word.

To quote Immunity Core's output in a reason and keep its words, quote it as the text form prints it, or leave a space after each cut value. A mark glued to more text in the same word, as in compact JSON (`"--token \cut{immunity:flag-value 11}"],"cuts":`), is read as the start of a value that goes on, and the rest of that word is cut as it would be after a real value. The reason is still recorded, every mark it quoted is kept, and `reason_cuts` lists what was cut.

The lists are data in `rules/secrets/`. Only the secret is replaced, never the program, the flag, the key or the delimiter around it. A cut stays inside one argument, so the arguments keep their count. In the text each cut is a mark, `\cut{<kind> <length>}`: the kind (`gitleaks:<rule id>`, `immunity:flag-value`, `detect-secrets:basic-auth`, `immunity:authorization`, `immunity:mysql-password`) and the length in characters. In the contract a backslash from the source is written `\u{5c}`, so a mark begins with the one bare backslash no source can write. Every printed program start also has `cuts`, one entry per piece cut with its `argument`, `kind` and `length`. That list is what a reader goes by. In the report's JSON, which does not escape a backslash, evidence carries the same `cuts`.

Arguments longer than 64 KiB together, and any other text from a source longer than that, are not searched at all and are withheld whole, each with the kind `immunity:too-long`. What ssh printed for a failed visit is read whole up to 4,352 bytes. Of a longer file Immunity Core reads only the time, the first line within its first 4,352 bytes, and the reason, the last line within the last 4 KiB before the blank space at its end, passing over at most 1 MiB of that blank space. A server's reason is never longer than 4 KiB. A field capped at 256 characters, such as a `detail_text`, is capped after the cut, and a mark in it is kept whole or left out. gitleaks's generic rule compares an allowlist with the whole line for every match, so a line with no newline packed with matches costs the square of its length. Measured in a release build on a loaded machine, such a line of 64 KiB took 29 ms and one of 1 MiB, the most a command line can be, 6.9 s. If the patterns do not load whole (`command-line.json` or gitleaks's file differs from `rules/secrets/SHA256SUMS`, a rule holds a key this build does not read, a pattern does not compile, or a planted invented secret checked at every load is not cut), every argument is withheld whole with the kind `immunity:no-patterns` and nothing is printed as it was. A verdict's reason that holds a recognised secret is kept with it cut, and the verdict is recorded; a key of a verdict that holds one is refused (`holds_secret`). A verdict that quotes what Immunity Core printed is always taken, and keeps its words when quoted as above.

What Immunity Core cannot recognise, so it may print it:

- a secret in a path or a working directory;
- a short flag whose meaning depends on the program, such as `sshpass -p x`, `docker login -p x` or `security add-generic-password -w x`, and a program name in capitals before `-p`, such as `MySQL -px`;
- a secret given alone as an argument, such as `ngrok config add-authtoken x` or an AWS secret key, when no pattern knows its shape;
- a value that begins with `-`, such as `--password -x`;
- a header other than `Authorization` whose name holds none of the words, and a bearer token in a form other than a header;
- a name that runs into other text with no boundary of those above, such as npm's `//registry/:_authToken=x`, where `authtoken` is not a word, or `/token=x`, where the name holds a `/`;
- a name written with a character outside ASCII, such as a non-breaking hyphen, or a value after a non-breaking space;
- a secret in a JSON body, such as `-d '{"password":"x"}'`;
- anything inside an encoded value.

A false cut costs only evidence text, since rules see the original.

The arguments of evidence, what the collector printed, the text of verdicts, and the reasons of answers and of statements about machines are kept cut, in their rows and in the journal. A command that prints them cuts them again with the set it loaded, so what a later set recognises is cut too. The store keeps that text with a backslash from the source written `\u{5c}`, as the contract writes it, so a mark is read only where Immunity Core made one, and a mark spelled out by a source is text, cut like any other. The collector's own log is not cut: it keeps every command line as `eslogger` gave it for up to a day ([event-level.md](event-level.md#who-can-read-the-log)).

## Files Immunity Core keeps

Everything lives in `~/Library/Application Support/ai.nuanu.immunity.core/` unless `--store` points elsewhere:

| Path | Holds |
|---|---|
| `store.db` | the store |
| `raw/<run>/` | raw input, copied only when it changed |
| `feeds/` | the latest OSV archive read whole per feed, with its record list |
| `indicators.json` | the indicator list, when the user gives one |
| `sweep/` | `sweep.sh`, `probe.sh`, `skip.txt` and the files the sweep leaves |
| `view.html`, `view/` | the HTML pages |
| `bin/immunity` | the copy of the core the login job runs, made by `immunity on` from a core not only root can replace; absent when the job runs a core where it is |

The store has format 9. `immunity run`, `immunity sample` and a newly starting `immunity watch` create a store when no file is at its path. `immunity on` starts the watcher. Every other command, the answers to a finding, `immunity owner` and `immunity verdict` among them, refuses a path with no store, and a watcher that is running never makes one. The store is created beside the path (`.store.db.making-…`), with its schema, format and id in one transaction. It is then linked to the final path with link(2), which succeeds only when that path is free. Two commands starting at once give one store. A command killed partway can leave its temporary file, which later commands ignore.

Opening a store never makes or changes a table, whatever the file holds. Every command checks the store's format and schema before it does anything else, a watcher at each reading too. An empty file, a file that is not SQLite and an SQLite file with no tables are refused as not a store. A store of another format, older or newer, is refused; the format is one row of `meta` and must be written as this build writes it, `9`, so `09` is not format 9. So is a damaged store: one whose schema is not exactly the one this format makes, or whose id is not one row of 32 lower-case hexadecimal characters. The schema is compared object by object as `sqlite_master` lists it: each table, index, view and trigger, the indexes and tables SQLite makes for itself included, by type, name, table and the text of the statement that made it, with comments taken out and every run of blank space made one space. That text holds every column, type, default, constraint, collation and key, `WITHOUT ROWID` and `AUTOINCREMENT`, so a store that differs in any of them, or holds one object too many, is refused. A refused file is not changed and nothing is made beside it. The refusal says what to do: move it aside or pass another `--store`, so that the next run makes a store from the beginning; for a newer format, use the version of Immunity Core that made it.

The store keeps every reading of the 20 runs the changes page lists and of the latest finished run. Of older ones it keeps the first and the last of each run of unchanged readings ([how-it-works.md](how-it-works.md#coverage)). A watcher's reading of the places one change touched keeps its raw copy as `watched-places-touched.txt`, apart from the copy of a reading of every place.

The collector keeps its own files under `/Library/Application Support/ai.nuanu.immunity.core/event-level`.

## Updating and removing

Immunity Core starts with a fresh format 9 store in its own directory. Use a format 8 build to read the previous store.

If you are switching from a source build with a format 8 store, run the previous binary's `off` to stop its watcher before you turn on the new service. If you installed the previous collector, save any logs you need before removing it with its own uninstaller.

Moving a Mac installed with the 0.2.0 app package requires the external installation layer's transition package.

To update an existing Immunity Core installation, run `git pull` and `./build`. If you use the service, run the new binary's `on` to update the [login job](core-service.md#update).

To remove Immunity Core, run `immunity off` to stop its [login job](core-service.md#turn-off). Delete the checkout and, to delete the data it recorded, the store folder at `~/Library/Application Support/ai.nuanu.immunity.core`. If you installed the collector, `sudo /bin/sh "/Library/Application Support/ai.nuanu.immunity.core/event-level/uninstall"` removes it and its logs. See [the collector](event-level.md).
